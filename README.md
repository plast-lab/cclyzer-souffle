# cclyzer

A tool for analyzing LLVM bitcode (generated by C, C++ or Rust compilers)
using Datalog, with [Soufflé](https://souffle-lang.github.io) as the Datalog
engine. It computes points-to sets, a call graph and type information.

## Requirements

- **LLVM 20 or newer** (headers, `llvm-config`, libclang). The build finds the
  newest `llvm-config-NN` on `PATH`, or set `LLVM_CONFIG=/path/to/llvm-config`.
  cclyzer reads bitcode from the same or older LLVM versions.
- **Soufflé built with 64-bit domains** (`-DSOUFFLE_DOMAIN_64BIT=ON`). The
  default 32-bit build cannot load cclyzer's facts.
- Boost (filesystem, program_options) and Python 3 (for the scripts).

There are three tested ways to get all of this.

### Nix

```sh
nix develop      # LLVM 22, 64-bit Soufflé, Boost, Python
make
```

### Docker

```sh
docker build -t cclyzer .
docker run --rm -v "$PWD/in:/in" cclyzer -i /in/program.bc -o /in/out
```

The image pins Ubuntu 24.04, Soufflé 2.5 and LLVM 22 (`--build-arg
LLVM_VERSION=21` for another one).

### Ubuntu / Debian

```sh
# LLVM from apt.llvm.org (Ubuntu 24.04 also ships llvm-20 itself)
wget https://apt.llvm.org/llvm.sh && sudo bash llvm.sh 22
sudo apt install llvm-22-dev libclang-22-dev \
     libboost-filesystem-dev libboost-program-options-dev python3 \
     bison flex cmake libffi-dev libsqlite3-dev zlib1g-dev mcpp

# Soufflé with 64-bit domains
git clone --depth 1 --branch 2.5 https://github.com/souffle-lang/souffle.git
cmake -S souffle -B souffle/build -DSOUFFLE_DOMAIN_64BIT=ON
sudo cmake --build souffle/build -j8 --target install

make
```

## Build

```sh
make                                     # everything
make -C src/logic ANALYSES=context-insensitive   # only some analyses
```

`make` builds the fact generator and one compiled analysis per
context-sensitivity variant (`build/logic/cclyzer-<analysis>`). Compiling the
Datalog takes a few minutes per analysis.

## Run

```sh
./cclyzer.sh -i program.bc -o out -a context-insensitive -j 8
```

Facts go to `out/facts/`, results to `out/results/` (one `.csv` per output
relation). Analyses:

- `context-insensitive` (default)
- `1-call-site-sensitive+heap`
- `2-call-site-sensitive+heap`
- `2-call-site-sensitive+2-heap`
- `selective` (experimental: context only for allocation wrappers and
  container-like functions)

For C, use `2-call-site-sensitive+heap`: without heap contexts, nearly all
memory comes from a few allocation wrappers (xmalloc, palloc), so the
context-insensitive heap is a handful of objects and the analysis is both
slower and less precise.

`cclyzer.sh` uses the compiled analysis when it exists and Soufflé's
interpreter otherwise. It does not write into the source tree, so several
runs can share one checkout.

### Analyse whole programs

cclyzer only analyses the code in its input. Give it **one bitcode file
containing every translation unit of the program**, including the program's
own static libraries. With a single `.c` file, calls into other files have no
body, so the call graph stops there and function pointers set up in those
files have no targets.

To get one file:

```sh
# small programs
clang -g -c -emit-llvm a.c -o a.bc && clang -g -c -emit-llvm b.c -o b.bc
llvm-link a.bc b.bc -o program.bc

# projects with their own build system: full LTO, keep lld's merged module
CC=clang CFLAGS="-flto -g" LDFLAGS="-flto -fuse-ld=lld -Wl,--save-temps" ./configure && make
# -> program.0.0.preopt.bc next to each linked program
```

The companion cclyzer-benchmarks repository builds 164 real programs this way
with one command.

`cclyzer.sh` warns (without stopping) when the input looks incomplete: no
`main`, many calls to undefined functions that are not standard C/C++/POSIX
functions, or many reachable indirect calls without a target. Names of
libraries you link on purpose can be listed in files named by
`CCLYZER_KNOWN_EXTERNALS` (colon-separated); `CCLYZER_NO_CHECKS=1` turns the
checks off.

### Local variables: SSA values, not memory

Unoptimized code (`-O0`) keeps every local variable and parameter in a stack
slot (`alloca`) and reads and writes it through memory:

```llvm
define ptr @id(ptr %p) {          ; static int *id(int *p) { return p; }
  %p.addr = alloca ptr            ; the stack slot for p
  store ptr %p, ptr %p.addr
  %0 = load ptr, ptr %p.addr
  ret ptr %0
}
```

Taken literally, every local is a memory object: each assignment is a store
into it and each use a load, and all values ever stored into it mix
(flow-insensitively). So before generating facts, the fact generator
promotes every local whose address is never taken to SSA values, as LLVM's
`mem2reg` pass does; `@id` above becomes `ret ptr %p`. Locals whose address
is taken stay memory objects, as they must:

```c
void set(int **pp) { *pp = &b; }
int main(void) { int *p = &a; set(&p); return *p; }   // p may point to b
```

This works on any input, including `-O0` code (whose functions are marked
`optnone`), and keeps debug information. On GNU make (whole program, `-O0`)
it promotes 89% of the stack slots and makes the analyses 2-6x faster with
smaller points-to sets. `fact-generator --no-mem2reg` keeps every stack slot
as an object, as earlier versions did.

### Contexts of stack objects

In `2-call-site-sensitive+heap`, heap and global objects get one call site
of context ("+heap"), and stack objects (locals whose address is taken,
by-value parameters) get the whole two-call-site method context: a stack
object belongs to one activation of its function. With a one-element
context for stack objects too, two activations that differ only in the
older call site would share their locals, and the second call site could
never separate a value that passes through one.

## Working on the analyses

The Datalog is in `src/logic/`. After a change, `make -C src/logic` rebuilds
the compiled analyses (minutes each). For fast iteration on small programs,
run the interpreter on existing facts instead:

```sh
souffle -j 8 --macro=TWO_CALL_SITE_SENSITIVE_HEAP=1 -F out/facts -D out2 src/logic/master.project
```

Tools to check a result (`<results>` is `out/results`, `<facts>` is `out/facts`):

```sh
scripts/stats.py <results> --facts <facts>   # reachable code, call graph, unresolved indirect calls, empty dereferences
scripts/empty-derefs.py <results> <facts>    # why dereferenced pointers have empty points-to sets
scripts/unmodelled.py <facts>                # library functions called without a model
```

In a sound result a dereferenced pointer has an empty points-to set only if
it is null or never points anywhere at runtime, so the empty dereferences are
the first thing to check after a change.

### Library models

Library functions (libc, libpq, zlib, ...) have no body in the bitcode, so a
call to one produces no points-to facts unless it has a model. Models are
one-line specs in `src/logic/points-to/library-models.dl`; the comment at the
top of the file explains each kind. For example:

```
lib_alloc("@strdup").          // returns a fresh object
lib_ret_arg("@strchr", 0).     // returns a pointer into argument 0
lib_out_alloc("@getline", 0).  // stores a fresh object into *argument 0
lib_callback("@qsort", 3, 0, 0).  // calls argument 3 with argument 0 as its parameter 0
```

`scripts/unmodelled.py` lists the functions still missing, ranked by call
sites. Functions that return a pointer almost always need a model; ones that
only read their pointer arguments (free, strlen, fprintf) need none.

## Tests

`tests/` has bitcode for coreutils 8.24 and PostgreSQL 9.5.2 client
programs. `make test-<program>` (e.g. `make test-ls`) analyses one coreutils
program.
